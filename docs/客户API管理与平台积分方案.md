# 客户 API 管理与平台积分方案

日期：2026-10-23  
版本：讨论稿，参考用户提供的 LT 安全管家 API 文档；包含 14 个平台，统一要求检测有标记后才能提交。  
说明：本文用于确认需求和开发范围，接口、字段及默认规则均为设计建议，不代表功能已开发或上线。

## 1. 功能目标

在现有“标记处理”下面增加“客户 API 管理”。管理员给客户开通 API，并按平台分别充值积分。所有平台都必须先检测号码是否有标记；有标记且符合平台处理条件、对应平台积分足够时，才能受理提交。客户最后通过 API 查询处理结果。

**已确认：三个无码平台同样需要检测有无标记。“无码”只表示不需要短信验证码，检测通过后仍由人工处理。**

主要流程：

> 管理员开通客户和平台 → 按平台充值积分 → 服务端检测号码 → 有标记且符合平台条件 → 校验对应平台积分及必要参数 → 扣积分并创建任务 → 进入现有标记处理 → 系统按平台周期复查号码标记状态 → 客户查询订单及最新标记状态。

参考 LT 文档的余额、批量提交、取消、状态和历史记录接口，增加平台列表和标记检测接口。

## 2. 后台“客户 API 管理”

### 2.1 客户列表

展示客户名称、绑定账号、责任代理、API Key、授权平台、启停状态、到期时间和最近调用时间。

每个客户提供以下操作：

- 创建 API Key 和 Secret，启用、停用、轮换 Secret。
- 选择一名启用的责任代理；客户 API 后续提交的订单固定进入该代理的处理队列。
- 开通或关闭某个平台。
- 查看各平台积分，按平台充值、扣减，查看积分流水。
- 查看检测记录、提交记录和处理结果。
- 查看接口文档和调用示例。

客户绑定独立账号；Key 用于认证身份，积分和订单属于客户账号。同一账号有多个 Key 时，共用该账号的平台余额，轮换 Secret 不改变余额。

Secret 仅在创建或轮换时显示一次。客户 API 不提供充值、修改余额、读取其他客户任务或回填处理结果的能力。

### 2.1.1 责任代理与订单归属

创建客户 API 时必须选择责任代理。责任代理必须是启用的代理或子代理账号；未绑定代理的客户 API 不允许启用，以避免订单进入无人处理的队列。

客户通过 API 成功提交订单时，系统将订单的分配代理字段设置为该客户 API 配置的责任代理。责任代理在现有“标记处理”工作台处理订单，客户只能通过客户 API 查询自己的提交和结果。

| 场景 | 规则 |
| --- | --- |
| 新增客户 API | 必须选择责任代理和至少一个授权平台 |
| 修改责任代理 | 只影响修改后的新订单；历史订单保留原责任代理 |
| 责任代理停用 | 不允许继续使用该代理创建或启用客户 API；管理员应转移未完成订单后再停用 |
| 代理与平台能力 | 客户 API 管理页只允许选择启用代理；客户提交接口落地时，再按平台处理能力校验责任代理是否可接单 |
| 多个责任代理 | 第一版每个客户 API 使用一个责任代理；后续如需按平台分配，再增加“平台责任代理”配置 |

客户 API 的责任代理配置与现有账号关系的自动分配分开。客户 API 下单优先使用明确配置的责任代理，不能因客户账号层级、创建人或模板变化而把新订单派给其他代理。

### 2.2 平台积分管理

示例：

| 客户 | 平台 | 是否开通 | 剩余积分 | 每号处理费用 |
| --- | --- | --- | ---: | ---: |
| 客户 A | 联通管家 | 是 | 5 | 1 |
| 客户 A | 百度 | 是 | 0 | 1 |
| 客户 A | 小米 | 是 | 20 | 2 |

在这个例子中，客户最多可以受理 5 个符合条件的联通管家号码，百度需要先充值，小米每受理一个号码扣 2 积分。

各平台余额独立，不能拿百度积分提交联通管家。充值和扣减需要记录操作人、数量、备注、时间、变动前余额和变动后余额。

建议第一版由管理员充值。代理能否给自己的客户充值、是否需要扣代理余额，作为单独的业务选择确认。

| 泰迪熊二次 | `td_second` |
| 腾讯 | `tengxun` |
| 360二次 | `qihu_second` |
| 百度 | `baidu` |

### 2.4 新增三个无码平台的接入规则

客户 API 对三个无码平台采用以下目标规则。现有业务可复用其人工处理、独立计费和退款基础，标记检测需要另外补接，不能将现有页面直接下单的行为当成 API 的免检规则。

| 项目 | 三个无码平台的规则 |
| --- | --- |
| 提交方式 | 批量提交手机或固话号码及备注，经服务端检测通过后进入代理人工处理队列 |
| 标记检测 | 与其他平台一样必须检测有无标记；有标记且符合平台条件才能提交 |
| 验证码 | 不需要验证码，不提供发码步骤 |
| 处理方式 | 提交前调用对应标记检测；责任代理先开始处理，再由自动巡检验证是否已无标记 |
| 平台余额 | 三个平台各自独立计费，不共用余额 |
| 普通与无码平台 | 泰迪熊与泰迪熊无码、腾讯与腾讯无码、360二次与360无码分别授权、分别扣费、分别查询任务 |
| 处理失败 | 按原实际扣款退回对应无码平台余额；重复失败不重复退款 |
| 已退款改成功 | 重新扣回对应平台费用，余额不足时拒绝改为成功；先改待处理再改成功也要补扣 |

例如客户的 `tengxun` 有积分、`wuma_tengxun` 没有积分时，不能使用腾讯无码。检测可接入同一底层平台查询服务，但授权、检测记录归属、处理队列和余额仍按客户选择的平台隔离。

三个无码平台需要配置各自的标记检测来源：

| API 处理平台 | 需要接入的检测类型 |
| --- | --- |
| `wuma_taidixiong` | 对应泰迪熊标记检测 |
| `wuma_tengxun` | 对应腾讯标记检测 |
| `wuma_360` | 对应 360 标记检测 |

具体检测接口和来源编码以实际平台配置及联调结果为准，不按名称相似自动选择。检测来源未配置、不可用或结果无法识别时，不得绕过检测创建处理订单。

新增平台的页面和业务代码已加入项目；数据库脚本、模板开通及部署状态以实际环境为准。具体接入说明见同目录的《标记无码平台接入说明.md》。客户 API 仍需按本文另外开发和联调。

## 3. 检测和提交规则

### 3.1 指定平台检测

本节的标记判定适用于全部 14 个平台，包括三个无码平台。检测必须指定平台，同一个号码在百度有标记，不代表在小米也有标记。

| 检测情况 | 是否可提交 | 处理方式 |
| --- | --- | --- |
| 有标记，符合该平台处理条件 | 是 | 还需校验积分、重复任务和必要参数 |
| 无标记 | 否 | 返回无标记，不扣处理积分 |
| 检测失败或结果无法识别 | 否 | 返回失败原因，可重试 |
| 有标记，但不符合该平台处理条件 | 否 | 返回具体原因 |

高频等平台继续使用各自的处理条件，不能把“任何标记”都当成该平台可处理的结果。

三个无码平台提供与其他平台一致的 `/check` 检测能力，返回有标记、无标记、检测失败及是否符合处理条件。检测异常不能伪造为有标记或无标记，也不能改为免检提交。

### 3.2 提交时按平台规则检查

所有平台：客户可以先检测、再决定是否提交，也可以直接调用提交接口。无论哪种方式，服务端都必须确认号码当前有可信、有效且符合条件的检测结果，不能相信客户自行传入的“有标记”。直接调用提交接口也必须由后台完成检测校验。

为了减少重复调用检测服务，可以短时间复用服务端保存的检测记录。记录必须绑定客户、平台和号码，并有有效期；建议先按 5 分钟设计，最终根据平台情况确定。缓存过期或没有记录时，提交接口重新检测。

客户端不必额外管理检测凭证，第一版提交参数保持接近 LT 文档的 `phones` 数组。

三个无码平台：在服务端检测有标记且符合平台条件后，继续校验客户和平台授权、号码格式、重复任务、对应平台余额，通过后扣费创建人工任务。无需短信验证码；责任代理先在工作台开始处理，随后自动巡检持续检测是否已无标记。

处理方式及验证码要求由服务端的平台配置决定。全部平台均要求检测通过，客户端不能传入“跳过检测”绕过门槛；检测来源尚未接通的平台不得开放受理处理能力。

### 3.3 积分与收费

- 处理费用按实际受理号码计算：`受理数量 × 该客户在该平台的单价`。
- 只有成功创建处理任务的号码才扣处理积分。
- 所有平台（包括无码平台）无标记、检测失败或不符合处理条件的号码不受理、不扣处理积分。
- 所有平台的无效号码、重复任务和积分不足号码，不扣处理积分。
- 所有平台的检测是否另收费尚未确定。建议第一版检测不扣处理积分，并限制调用频率；三个无码平台适用相同规则。
- 如果选择检测收费，需要单独定义检测单价、扣费时点和失败是否退款，不能混入处理费用。

## 4. 批量提交：逐个号码受理和扣费

参考 LT 文档，每个号码单独返回是否提交、是否扣费及原因。

全部 14 个平台逐号进行标记判定，包括三个无码平台。仅检测有标记且符合处理条件的号码，才可能按授权、格式、防重、余额和必要参数规则受理。无码平台同样可能返回 `unmarked`、`check_failed`、`not_submittable` 等结果。

建议按请求中的号码顺序受理。余额只能支付部分号码时，前面符合条件且有足够积分的号码正常受理，后面的号码返回积分不足，不影响已受理号码。

| 提交结果 | `result` 建议值 | 是否扣处理积分 |
| --- | --- | --- |
| 已受理并创建任务 | `submitted` | 是 |
| 当前客户在同平台有未完成任务 | `duplicate` | 否 |
| 同一批次内号码重复 | `duplicate_in_batch` | 否 |
| 号码格式不正确或该平台不支持 | `invalid` | 否 |
| 无标记 | `unmarked` | 否 |
| 检测失败 | `check_failed` | 否 |
| 有标记但不符合平台处理条件 | `not_submittable` | 否 |
| 对应平台积分不足 | `insufficient_balance` | 否 |
| 缺少验证码等必要参数 | `missing_parameter` | 否 |

未完成任务的重复判断范围建议为“客户账号 + 平台 + 号码”。不同平台分别判断；已完成后能否当天重提，需要与现有当天重复提交限制一起确定。

手机、座机、400 号码的支持范围按各平台配置返回。LT 示例中的号码规则可以作为联通管家的参考，不能直接套用到全部平台。

三个无码平台当前支持手机、固话批量提交及去重；具体格式与当前服务端保持一致，不直接照搬 LT 的位数限制。

## 5. 客户 API 接口总览

客户 API 当前实现的接口前缀为 `/open/v1/mark/customer`，平台放在路径中。这样所有平台共用一套接口约定，例如联通管家的余额路径为 `/open/v1/mark/customer/ltgj/balance`。

| 功能 | 方法 | 建议路径 | 说明 |
| --- | --- | --- | --- |
| 平台列表 | GET | `/platforms` | 查询已授权平台、积分、单价、提交模式、检测及验证码能力、支持的号码类型 |
| 平台余额 | GET | `/{platformCode}/balance` | 查询该平台剩余积分 |
| 号码检测 | POST | `/{platformCode}/check` | 全部平台检测有无标记及是否符合处理条件，包含三个无码平台 |
| 批量提交 | POST | `/{platformCode}/submit` | 全部平台逐号校验标记、授权和积分；检测通过后受理，无码平台进入人工队列 |
| 取消订单 | POST | `/{platformCode}/cancel` | 取消尚未实际处理的排队任务并退款 |
| 查询订单详情 | GET | `/orders/{orderId}` | 查询自己的订单及所有号码明细 |
| 订单列表 | GET | `/orders?platformCode=...` | 分页查询自己在指定平台的订单记录 |

路径中的平台编码必须属于当前客户和 Key 的有效授权范围。普通腾讯、泰迪熊二次等平台涉及验证码，需要另外适配发码接口和提交参数；`wuma_tengxun`、`wuma_taidixiong`、`wuma_360` 不需要验证码。

客户不需要调用独立的“添加监测号码”接口。号码在提交成功、订单明细创建后，系统自动加入标记复查；客户通过状态和历史接口读取复查结果。

平台列表建议增加以下能力字段，便于客户按平台选择调用流程：

| 字段 | 含义 | 三个无码平台的值 |
| --- | --- | --- |
| `submit_mode` | 提交模式，无码平台检测通过后人工处理 | `manual_after_check` |
| `supports_check` | 是否提供标记检测 | `true` |
| `require_mark_check` | 提交前是否必须通过标记检测 | `true` |
| `requires_sms_code` | 提交是否需要短信验证码 | `false` |

这些字段描述接入完成后的目标能力，由服务端返回，不能作为客户端提交参数覆盖后台规则。全部开放的平台均应支持检测且要求检测通过；检测来源尚未接通的平台应标为未就绪，不得显示为可以提交。余额、状态、历史记录和按条件取消接口仍按同一套约定设计。

### 5.1 鉴权和响应格式

复用现有 Key/Secret 请求头：

```http
X-API-Key: YOUR_API_KEY
X-API-Secret: YOUR_API_SECRET
Content-Type: application/json
```

建议客户 API 参考 LT 的响应风格：`code=0` 表示本次接口调用成功，`code!=0` 表示接口级错误，具体编码在开发时统一定义。现有系统内部响应格式通过客户 API 层转换。

批量接口返回 `code=0` 只表示已经完成逐号处理，是否真正受理必须查看 `details[].result`，不能只检查顶层 `code`。

### 5.2 余额查询

请求：`GET /open/v1/mark/customer/ltgj/balance`。

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "platform_code": "ltgj",
    "remain": 5,
    "unit_cost": 1
  }
}
```

`remain` 表示积分余额。单价为 1 时，余额数值与可处理条数相同；单价不为 1 时，需要按单价计算。

### 5.3 号码检测

请求：`POST /open/v1/mark/customer/ltgj/check`。

```json
{
  "phones": ["13800138001", "02012345678"]
}
```

响应示例：

```json
{
  "code": 0,
  "msg": "检测完成",
  "data": {
    "details": [
      {
        "phone": "13800138001",
        "result": "marked",
        "marked": true,
        "can_submit": true,
        "message": "有标记，符合平台处理条件"
      },
      {
        "phone": "02012345678",
        "result": "unmarked",
        "marked": false,
        "can_submit": false,
        "message": "无标记"
      }
    ]
  }
}
```

检测失败时返回 `result=check_failed`、`marked=null`、`can_submit=false`。`can_submit` 表示检测条件通过，实际下单仍需校验积分、重复任务等条件。

此响应结构同样适用于三个无码平台。例如 `POST /open/v1/mark/wuma_tengxun/check` 应返回腾讯无码平台对应号码的标记检测结果。检测来源尚未接通或查询失败时返回明确错误，不得因此免检受理。

### 5.4 批量提交

请求：`POST /open/v1/mark/customer/ltgj/submit`。

```json
{
  "request_no": "customer-20261023-0001",
  "phones": ["13800138001", "13800138002", "02012345678", "4001234567"],
  "agent_remark": "第一批"
}
```

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `request_no` | string | 是 | 客户生成的唯一请求编号，重试时使用原编号 |
| `phones` | array | 是 | 号码数组，建议第一版单次不超过 100 个 |
| `agent_remark` | string | 否 | 客户提交备注，参考 LT 限制为最多 200 字 |

`agent_remark` 在本接口中表示客户随订单提交的备注，后台需要与处理人员的内部手动备注分开保存和展示。

响应示例，假设初始余额 5 积分、每号 1 积分：

```json
{
  "code": 0,
  "msg": "提交完成",
  "data": {
    "request_no": "customer-20261023-0001",
    "inserted": 1,
    "total": 3,
    "remain": 4,
    "charged_credits": 1,
    "details": [
      {
        "phone": "13800138001",
        "record_id": 10001,
        "result": "submitted",
        "billed": true
      },
      {
        "phone": "13800138002",
        "record_id": 9988,

```

- `inserted`：本次新受理数量，不包含已有重复任务。
- `total`：号码格式有效且去重后的数量，不代表都符合受理条件；示例中为 3。
- `details`：按原输入顺序逐项返回，包括无效号码和批内重复号码。
- `record_id`：单个号码的处理明细 ID，用于查询和取消；与后台批次订单 ID 区分。
- `billed`：该明细是否发生扣款。幂等重试返回原受理结果时，该字段仍描述原受理行为，不表示又扣了一次。

已受理不等于已处理完成，最终结果通过状态查询获得。

三个无码平台使用相同的提交请求结构，例如 `POST /open/v1/mark/customer/wuma_tengxun/submit`，请求中的 `request_no`、`phones`、`agent_remark` 含义不变，无需验证码。服务端仍必须读取有效检测记录或重新检测，只有有标记且符合条件的号码才能受理；客户端无须额外传检测凭证。响应中的 `remain` 和 `charged_credits` 只涉及 `wuma_tengxun` 余额；任务由对应无码人工队列处理，不进入普通腾讯的自动处理流程。

## 6. 取消和状态规则

取消请求：`POST /open/v1/mark/ltgj/cancel`，请求体为 `{"record_id":10001}`。

- 只能取消当前客户、当前平台下自己的任务。
- 只有排队且尚未被领取、派发或提交上游的任务可以取消。
- 已经实际处理的任务，即使页面尚未刷新，也不能取消。
- 取消成功后退还原实际扣款金额，不能简单固定退 1 积分。
- 重复取消返回已有取消结果，不能重复退款。

参考 LT 的主要状态含义：

| 对外状态 | 状态文字 | 说明 |
| ---: | --- | --- |
| 0 | 排队中 | 尚未实际处理，符合条件时可取消 |
| 1 | 处理中 | 已领取、派发或进入实际处理，不能取消 |
| 2 | 已完成 | 处理成功 |
| 3 | 已退款 | 系统退款已成功入账，保留原处理结果和退款原因 |
| 5 | 已取消 | 客户取消成功，退款已成功入账 |

这些状态是客户 API 的建议约定，不能直接复制后台内部数字状态。尤其自动处理平台、已派发上游的任务，需要按真实处理进度转换。

三个无码平台由人工反馈结果；接入取消功能时，需要补充人工领取或开始处理的记录，不能仅凭当前“待处理”状态认定一定可以取消。取消与人工反馈必须协调状态，避免取消退款后仍继续处理。

三个无码平台当前规则是失败自动退回对应平台费用。其他平台失败是否一律退款仍需逐平台确认。如果允许失败不退款，或退款存在重试过程，需要在接口定稿时补齐“处理失败”和“退款中/退款失败”的表达；实际未退到账不能显示“已退款”。

状态轮询可参考 LT 建议，每 5–10 分钟查询一次；最终按照各平台处理速度制定调用频率。

### 6.1 订单标记复查状态

订单处理状态表示任务是否排队、处理、完成、退款或取消；号码标记复查状态表示该号码**当前是否仍有标记**。两者独立展示，不能互相替代。

例如，订单已经处理完成后，复查仍可能显示“仍有标记”；订单处于处理中时，复查也可能已经检测到“无标记”。

| `monitor_status` | 含义 | 是否继续复查 |
| --- | --- | --- |
| `PENDING` | 订单已受理，等待首次复查 | 是 |
| `MONITORING` | 最近一次检测仍有标记 | 是 |
| `CLEARED` | 最近一次检测无标记，已自动停止 | 否 |
| `CHECK_FAILED` | 最近一次检测失败，保留任务等待下一轮 | 是 |
| `EXPIRED` | 达到最长复查期限仍未检测到无标记 | 否 |
| `STOPPED` | 订单取消、退款终止或管理员手动停止 | 否 |

状态查询和历史记录建议增加以下字段：

```json
{
  "monitor_status": "MONITORING",
  "current_marked": true,
  "first_checked_at": "2026-10-23 14:00:00",
  "last_checked_at": "2026-10-23 14:30:00",
  "next_check_at": "2026-10-23 15:00:00",
  "monitor_expires_at": "2026-10-30 14:00:00",
  "monitor_stopped_at": null,
  "last_check_result": "有标记",
  "last_check_error": null
}
```

`current_marked` 在检测失败前保留上一次成功检测的结果；首次检测尚未完成时为 `null`。客户应结合 `monitor_status` 与 `last_checked_at` 判断数据是否新鲜，不能把历史的 `current_marked=true` 误解成最新一次检测成功。

### 6.2 自动复查策略：复用现有巡检框架

现有自动巡检已经具备按平台配置间隔、批量数量、下次运行时间、运行日志和定时调度的基础。客户 API 的订单标记复查应复用这套调度框架，但不能直接复用现有自动处理逻辑。

现有自动处理巡检会扫描待处理订单，并可能自动将订单结果改为成功或失败。新增复查只更新订单明细关联的标记复查记录，不修改订单处理状态、不自动退款、不重新扣费，也不自动代替人工或上游处理。

建议为现有巡检策略增加 `policy_type`：

| 策略类型 | 建议值 | 扫描对象 | 执行结果 |
| --- | --- | --- |
| 现有自动处理巡检 | `AUTO_PROCESS` | 待处理订单明细 | 按现有规则可能更新处理成功或失败 |
| 新增号码标记复查 | `MARK_MONITOR` | 已受理且仍在复查中的订单明细 | 只写入最新标记状态与复查历史 |

`MARK_MONITOR` 按平台配置以下参数：

| 配置 | 作用 | 建议初始值 |
| --- | --- | --- |
| 检测间隔 | 同一平台两次复查的最短间隔 | 30 分钟；按平台调整 |
| 单次批量数量 | 一次调度最多检测的订单明细数 | 100 |
| 最长复查期限 | 从订单受理或首次检测起的最长持续时间 | 7 天；按平台调整 |
| 失败重试 | 检测失败后下次尝试的间隔 | 下一周期；必要时加短暂退避 |
| 连续失败告警阈值 | 达到次数后提醒管理员检查检测来源 | 3 次 |

所有 14 个平台都按“检测有标记才受理”的规则接入；是否实际开启提交后复查、间隔及最长期限可按平台单独配置。检测来源未配置或不可用时，不应创建可执行的复查任务，并且相应平台不得开放提交受理。

### 6.3 复查任务生命周期

1. 客户提交号码，服务端首次检测为有标记且符合平台条件，积分扣除、订单明细创建成功。
2. 同一事务为该 `orderItemId` 创建一条复查任务，记录客户、平台、号码、首次结果、下次检测时间和最长截止时间。
3. `MARK_MONITOR` 到期执行时，只读取仍需复查的订单明细，调用对应平台检测并写入一次复查历史。
4. 检测仍有标记：更新为 `MONITORING`，安排下一次检测。
5. 检测无标记：更新为 `CLEARED`，记录停止时间，不再检测。
6. 检测失败：更新为 `CHECK_FAILED`，记录错误和失败次数，保留任务在下一轮重试。
7. 到达最长复查期限仍未检测到无标记：更新为 `EXPIRED`，停止检测。
8. 客户取消且退款成功、订单被终止，或管理员手动停止时：更新为 `STOPPED`，清除后续检测计划。

复查任务以 `orderItemId` 为主键关联，不能设计为客户任意添加号码的独立监测列表。每次检测保存历史，以便客户和管理员查看“何时有标记、何时无标记、何时检测失败”。

## 7. 必须保证的订单和积分一致性

1. **请求幂等。** 同一客户的同一 `request_no`、相同内容，返回原完整结果，不重复创建或扣费；同一编号不同内容返回冲突。返回原结果应先于当前余额、检测有效期等校验。
2. **逐号扣费准确。** 扣积分、创建受理明细、创建复查任务、保存流水和提交结果保持事务一致，不能出现扣了积分却没有任务，或受理成功却漏建复查任务。外部检测放在余额事务之外执行。
3. **并发余额准确。** 同平台同时提交时锁定或原子更新余额，保证不会超扣。批内按输入顺序计算可受理号码。
4. **重复任务准确。** 并发请求提交相同客户、平台、号码时，服务端仍能保证只存在一个未完成任务，不能只靠先查询再插入。
5. **取消与处理、复查互斥。** 取消和任务领取、派发、人工反馈、复查调度必须通过服务端原子状态变更协调，不能出现已取消退款后仍回填为成功或继续安排复查的冲突。
6. **退款准确。** 退款关联原扣款，退回原平台，一次扣款不能重复退款。已退款任务改回成功时，应检查退款记录并按规则补扣，不能仅看上一个状态。
7. **数据隔离。** 检测缓存、订单、余额和查询结果均按客户账号及平台隔离，客户参数不能指定另一个客户身份。

部分号码被拒绝属于正常的逐号业务结果；如果发生数据库等系统异常，不得返回未实际落库的受理成功结果。客户可使用原请求编号安全查询或重试。

## 8. 项目中可复用与需新增的部分

现有项目已具备 Key/Secret 凭据管理、按账号和平台维护余额、积分流水、预查询、下单及处理工作台等基础。新增的三个无码平台已提供独立提交页、人工工作台入口和按平台计费、退款规则，客户 API 可以复用其业务基础。

需要新增或补齐：

- “标记处理”下的客户 API 管理入口，以及客户平台授权和充值操作。
- 客户专用的检测、提交、余额和自己订单查询权限，与现有任务读取、结果回填权限分开。
- 为全部平台接入标记检测和服务端检测记录及短期复用，统一“有标记、无标记、检测失败、不可处理”的判定。
- 全部平台落实检测门槛，再按平台决定是否需要验证码、采用自动处理还是人工处理。三个无码平台补接检测，检测通过后由代理开始处理，不发验证码；开始处理后参与自动巡检。
- 在平台列表返回能力信息，并将三个无码平台与对应普通平台的权限、余额、订单和流水分别隔离。
- 逐号受理、部分余额受理、请求幂等和完整结果保存。
- 排队任务取消及与任务领取、派发相配套的状态控制。
- 订单来源、API 凭据、客户请求编号与积分流水的关联。
- 在现有巡检策略上增加 `MARK_MONITOR` 类型、订单明细复查任务和复查历史；复用调度和平台周期配置，但不复用自动改订单结果的逻辑。
- 在客户状态与历史接口返回最新标记状态、复查时间、下次检测时间、期限和检测失败原因。
- 客户接口文档、限流、调用记录及联调示例。

现有部分提交规则与本方案不同，例如当天重提限制，需要明确取舍后调整。现有无码平台业务没有提交前检测，当前预查询还会提示直接提交；客户 API 必须补接检测来源和统一检测校验，不能原样照搬该行为。免费检测也需要核对当前检测执行链的计费行为，避免误扣其他余额。

- 同目录的《标记无码平台接入说明.md》，包括 `backend/sql/mark_wuma_manual_processing.sql` 的生效步骤。

## 10. 验收清单

- 给联通管家充值，不改变同客户其他平台的余额。
- 未开通平台不能提交；平台余额不足不受理、不扣处理积分。
- 全部平台（包括三个无码平台）无标记、检测失败和不符合平台条件的号码均不会误受理；直接调用提交接口也必须经过服务端检测校验。
- 三个无码平台必须检测有标记且符合条件后才可提交，不要求短信验证码；受理后进入人工队列，代理开始处理后触发自动巡检。
- 三个无码平台的 `/check` 正确返回有标记、无标记和检测失败等结果，提交接口按相同规则判断，不能伪造或跳过检测。
- 任意平台检测来源未配置或不可用时，禁止免检创建处理订单，不扣处理积分。
- 普通腾讯与腾讯无码、泰迪熊与泰迪熊无码、360二次与360无码分别授权、分别扣费；一个平台充值、退款不改变另一个平台余额。
- 平台列表正确返回三个无码平台“检测后人工处理”、支持检测、必须通过检测、不需要验证码的目标能力信息；尚未完成检测接入时不得显示为可提交。
- 客户提交成功后，系统自动创建对应订单明细的复查任务；客户无需调用独立接口添加监测号码。
- 每个平台按其 `MARK_MONITOR` 策略的周期复查；复查只更新当前标记状态和复查历史，不改变订单处理状态、积分或退款。
- 检测到无标记时状态变为 `CLEARED` 并停止复查；达到最长期限时变为 `EXPIRED` 并停止复查。
- 检测失败记录错误与时间，并在下一周期重试；取消、退款终止或管理员停止后状态变为 `STOPPED`，不再复查。
- 状态和历史接口同时正确返回订单处理状态与号码标记复查状态，避免将“处理完成”误当成“已无标记”。
- 批量请求逐项返回结果，扣款数量与实际受理数量一致。
- 部分余额只受理可支付的号码，并明确返回剩余号码积分不足。
- 并发提交不会超扣，不会创建重复未完成任务。
- 同请求编号重试只受理、扣款一次，返回原完整结果。
- 客户只能查询、取消自己的任务，且按平台隔离。
- 排队取消只退款一次；实际处理已开始后不能取消。
- 无码平台人工领取、反馈与客户取消并发时，状态和退款结果保持一致。
- 退款金额等于原实际扣款，退款未完成不会误报已退款。
- 无码平台失败自动退款，已退款订单直接或先经待处理再改成功时均按规则重新扣费，余额不足拒绝改为成功。
- 订单进入现有工作台，可以追踪客户、来源和请求编号。
- 停用 Key 或轮换 Secret 后，旧凭据不能继续使用。

| --- | --- |
| 检测是否收费 | 全部平台第一版建议免费检测并限流，三个无码平台适用相同规则 |
| 无积分是否允许检测 | 检测免费时建议允许，但对应平台积分不足不允许受理处理 |
| 提交后是否自动复查 | 建议所有已受理订单明细自动创建复查任务；平台可单独关闭复查能力 |
| 复查停止条件 | 检测无标记、达到最长复查期限、客户取消且退款成功、订单终止或管理员停止 |
| 复查间隔与期限 | 管理员按平台配置；建议默认 30 分钟、最长 7 天 |
| 复查收费 | 第一版建议不另收费，只限制周期、批量和活跃任务数量；如收费需单独计费与流水规则 |
| 每号处理费用 | 按客户、平台配置；可先默认每号 1 积分 |
| API 与网页是否共用余额 | 默认共用绑定账号的各平台余额 |
| 余额不够整批时 | 按输入顺序部分受理，逐号返回积分不足 |
| 失败是否全部退款 | 三个无码平台沿用失败自动退款；其他平台需要逐平台确认 |
| 完成后当天是否可重提 | 与现有当天防重规则统一确定 |
| 代理能否充值客户 | 第一版先由管理员充值 |
| 首批接入哪些平台 | 从当前 14 个平台中逐个核对检测来源、验证码要求、人工或自动处理及取消能力；检测未接通的平台不能免检受理 |

## 12. 当前已实现的客户 API 管理与第一期调用接口

已新增“客户API管理”菜单、客户 Key/Secret、授权平台和责任代理配置。客户 API Key 与既有“自动化API管理”的 Key 类型隔离：客户 Key 不能读取代理待处理队列，也不能回填订单处理结果。

客户 API 列表支持删除，需拥有 `server:markCustomerApi:remove` 权限。管理员确认后，系统在同一事务内删除该客户凭据及平台授权，删除后旧 Key/Secret 无法再通过鉴权；已进入处理流程的请求不受此操作撤回。客户账号、平台积分、历史订单、自动巡检及调用日志保留。删除接口为后台管理用的 `DELETE /server/markCustomerApi/{id}`，仅接受 `CUSTOMER` 类型凭据，不属于客户开放接口。

已部署环境升级删除功能时，先执行增量脚本 `backend/sql/mark_customer_api_remove.sql`，再发布后端和前端；新环境执行完整的 `mark_customer_api_management.sql` 即包含删除权限。管理员默认拥有删除权限，其他角色需单独授权。

客户调用第一期接口时使用以下请求头：

```http
X-API-Key: YOUR_API_KEY
X-API-Secret: YOUR_API_SECRET
Content-Type: application/json
```

| 接口 | 作用 |
| --- | --- |
| `GET /open/v1/mark/customer/platforms` | 查询当前客户已授权且账号已开通的平台、单价和剩余次数 |
| `GET /open/v1/mark/customer/{platformCode}/balance` | 查询指定已授权平台的积分余额 |
| `POST /open/v1/mark/customer/{platformCode}/check` | 检测号码是否有标记以及是否符合处理条件 |
| `POST /open/v1/mark/customer/{platformCode}/submit` | 服务端再次检测后创建订单，并将订单分配给责任代理 |
| `GET /open/v1/mark/customer/orders?platformCode=...` | 查询当前客户在指定授权平台的订单 |
| `GET /open/v1/mark/customer/orders/{orderId}` | 查询当前客户自己的订单详情和号码明细 |

提交请求的 `requestNo` 必填；也兼容参考文档中的 `request_no`。客户备注字段使用 `remark`，也兼容 `agent_remark`。每次提交都在服务端重新检测，任何号码检测失败、无标记或不符合处理条件时，当前整批请求不受理、不扣积分。

部署前必须先执行 [mark_customer_api_management.sql](../backend/sql/mark_customer_api_management.sql)，再部署后端和前端代码；重新登录后，管理员会在“标记业务管理”下看到“客户API管理”。

以上为本轮讨论后的方案建议。确认其余业务规则后，再继续完成定时复查、取消、逐号部分受理及完整的客户状态接口。
