## 结论

白天多人使用时的卡顿主要来自 Java 进程和数据库访问链路，不是 `query-tdx` Node 服务占满 CPU。CodeGraph 追踪了代理工作台 `ProcessWorkbench`、订单明细 Mapper 和公共 HTTP 客户端；正式机线程采样进一步确认，Apache HttpClient 的 `idle-connection-evictor-1` 线程曾持续占用约 90% CPU。

根因是 `HttpConf.KEEP_ALIVE_TIMEOUT` 默认值为 `0`，而 `HttpUtils` 将它传给 HttpClient 的空闲连接回收器，回收线程没有等待时间而忙循环。除此之外，Tomcat 请求线程数、数据库连接池、MariaDB 内存和首屏查询也存在不匹配：Tomcat 最多 800 个线程争抢 20 个数据库连接，连接池耗尽时单个请求最多等待 60 秒；MariaDB Buffer Pool 只有 128MB，订单列表查询出现 `Using temporary; Using filesort`。

## 已完成的代码和配置修改

### 1. 修复 Java CPU 忙循环

文件：`backend/geek-common/src/main/java/com/geek/common/utils/http/HttpConf.java`

```java
public static int KEEP_ALIVE_TIMEOUT = 30000;
```

同时保留 HttpClient 连接池和过期连接回收功能。30 秒为连接空闲回收周期，避免设置为 0 造成忙循环。

### 2. 收敛 Tomcat 和 Druid 并发

运行时配置文件被项目 `.gitignore` 忽略，已写入本地配置并随正式 JAR 发布：

| 配置 | 原值 | 当前值 |
| --- | ---: | ---: |

没有直接放大数据库连接池，先让请求排队上限与数据库实际处理能力匹配。

### 3. 优化订单明细查询

新增增量脚本：`backend/sql/mark_performance_indexes.sql`。脚本是幂等的，只添加缺失索引：

```sql
idx_mark_order_item_created_id_order
  (create_time, id, order_id)

idx_mark_order_item_status_created_id
  (process_status, create_time, id, order_id)
```

正式库已执行并重新分析表。待处理轮询查询使用第二个索引后，执行计划从 `Using filesort` 变为按索引读取；无状态筛选的首屏列表在 Mapper 中条件使用时间索引，状态筛选仍使用状态索引。

对应查询文件：`backend/geek-server/src/main/resources/mapper/server/MarkOrderItemMapper.xml`。新建数据库时，两个索引也已加入 `backend/sql/mark_business_minimal.sql`。

### 4. 降低前端首屏压力

文件：`frontend/ruoyi-geek-vue3/src/views/server/mark/agent/components/ProcessWorkbench.vue`

- 默认每页从 90 条改为 30 条；
- “屏蔽账户”选项改为打开下拉框时才请求；
- 账户选项请求增加缓存和并发请求复用，屏蔽/解除屏蔽后才强制刷新。

前端已重新执行 `npm.cmd run build:prod` 并部署管理端静态文件。

### 5. 调整 MariaDB 运行参数

新增服务器配置文件：`ops/60-query-performance.cnf`，已安装到正式机 `/etc/mysql/mariadb.conf.d/60-query-performance.cnf`：

```ini
[mysqld]
innodb_buffer_pool_size = 256M
tmp_table_size = 32M
max_heap_table_size = 32M
thread_cache_size = 32
table_open_cache = 1024
```

MariaDB 已重启并成功加载，当前 Buffer Pool 为 256MB。该值按 2GB 服务器和 Java 最大堆 1GB 保守设置，后续应继续观察 Swap 后再决定是否提高到 384MB。
