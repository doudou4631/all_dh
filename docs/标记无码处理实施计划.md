# 标记无码处理实施计划

> 文档状态：方案评审稿  
> 编制日期：2026-09-18  
> 实施范围：无码业务独立建设，首期支持泰迪熊、360、腾讯，代理人工处理

## 1. 项目目标

在现有“标记业务管理”中新增“标记无码处理”业务分类。用户按具体平台提交号码，系统生成独立订单并扣除对应平台次数；订单自动分配给所属代理，由代理人工处理并回填成功或失败；用户可以查看结果，失败号码自动退回对应次数。

无码业务与现有泰迪熊、360、腾讯业务完全隔离，包括：

- 平台编码隔离；
- 菜单和页面入口隔离；
- 订单队列隔离；
- 用户及代理的平台余额隔离；
- 资金/次数流水隔离；
- 查询统计隔离；
- 后续自动化扩展隔离。

首期不接第三方平台接口、不需要验证码、不自动处理。

## 2. 已确认的业务定义

“无码”是业务分类，不是一个实际处理平台。首期包含三个子平台：

| 业务分类 | 平台名称 | 内部平台编码 | 处理方式 |
|---|---|---|---|
| 标记无码处理 | 无码-泰迪熊 | `wuma_taidixiong` | 代理人工处理 |
| 标记无码处理 | 无码-360 | `wuma_360` | 代理人工处理 |
| 标记无码处理 | 无码-腾讯 | `wuma_tengxun` | 代理人工处理 |

平台编码只在管理员平台管理、接口、数据库、日志和排错场景显示。普通用户及代理页面统一显示中文名称，例如“无码-泰迪熊”。

## 3. 菜单规划

建议菜单结构如下：

```text
标记业务管理
├─ 用户端
│  └─ 标记无码处理
│     ├─ 泰迪熊
│     ├─ 360
│     └─ 腾讯
└─ 代理处理
   └─ 标记无码处理
      ├─ 泰迪熊
      ├─ 360
      └─ 腾讯
```

为避免用户混淆，页面标题、任务记录和平台列显示完整业务名称：

- 无码-泰迪熊；
- 无码-360；
- 无码-腾讯。

### 3.1 用户端菜单

三个用户端子菜单使用专用的无码提交页面，路由参数分别传递实际平台编码：

```json
{"platformCode":"wuma_taidixiong","platformName":"无码-泰迪熊"}
```

```json
{"platformCode":"wuma_360","platformName":"无码-360"}
```

```json
{"platformCode":"wuma_tengxun","platformName":"无码-腾讯"}
```

### 3.2 代理端菜单

三个代理端子菜单复用现有代理处理工作台组件，通过不同的 `platformCode` 隔离队列。

每个平台只加载本平台订单，不允许无码订单进入现有普通泰迪熊、360、腾讯队列。

## 4. 平台管理的作用与新增配置

当前“平台管理”并不仅是展示配置，它是标记业务的平台总开关和映射来源，主要影响：

1. 用户端是否允许提交该来源平台；
2. 代理端是否允许处理该目标平台；
3. 来源平台如何映射到代理处理平台；
4. 用户和代理菜单是否显示；
5. 代理管理的充值平台列表是否出现；
6. 用户可用平台和模板平台是否有效；
7. 平台显示名称及排序。

首期新增三条一对一映射：

| 来源名称 | 来源编码 | 目标名称 | 目标编码 | 建议排序 |
|---|---|---|---|---:|
| 无码-泰迪熊 | `wuma_taidixiong` | 无码-泰迪熊 | `wuma_taidixiong` | 20 |
| 无码-360 | `wuma_360` | 无码-360 | `wuma_360` | 21 |
| 无码-腾讯 | `wuma_tengxun` | 无码-腾讯 | `wuma_tengxun` | 22 |

三类开关必须同时开启后配置才生效：

```text
source_enabled  = 0  用户端来源开启
target_enabled  = 0  代理端目标开启
mapping_enabled = 0  映射启用
```

平台关闭后的预期行为：

- 关闭来源：用户菜单被过滤，后端拒绝新提交；
- 关闭目标：代理菜单被过滤，不能继续进入该平台工作台；
- 停用映射：该平台整体失效，不出现在充值平台选项中；
- 已产生的历史订单和流水仍保留，不删除数据。

## 5. 用户提交方案

### 5.1 页面功能

新增无码专用提交页，包含：

- 当前平台名称；
- 当前剩余次数；
- 每个号码所需次数；
- 号码粘贴输入；
- 手机号/固话提取及去重；
- 有效、重复、无效数量统计；
- 用户备注；
- 提交前确认；
- 任务记录；
- 状态、处理时间和代理处理结果查询；
- 记录导出。

无码页面不显示：

- 一键预查询；
- 查询结果选择；
- 验证码；
- 第三方接口结果；
- 自动检测状态。

### 5.2 提交接口

建议复用现有普通订单接口：

```http
POST /server/markUser/order
```

示例：

```json
{
  "platformCode": "wuma_taidixiong",
  "platformName": "无码-泰迪熊",
  "phones": ["13800138000", "13900139000"],
  "requestNo": "客户端生成的唯一请求号",
  "remark": "用户备注"
}
```

后端继续执行现有的重要校验：

- 登录用户和权限校验；
- 平台是否启用；
- 平台是否在用户模板范围内；
- 号码格式、去重和空列表校验；
- 当日重复提交校验；
- 平台余额是否充足；
- `requestNo` 幂等校验；
- 代理归属计算；
- 订单、明细、扣费流水在同一事务内落库。

## 6. 订单与处理状态

首期复用现有 `mark_order` 和 `mark_order_item`，不新建重复订单表。

### 6.1 订单级状态

| 字段 | 值 | 含义 |
|---|---|---|
| `order_status` | `0` | 待处理 |
| `order_status` | `1` | 处理中或部分完成 |
| `order_status` | `2` | 全部完成 |

现有代码会在用户提交后自动审核通过，因此首期不增加人工审核环节。

### 6.2 号码明细状态

| 字段 | 值 | 含义 |
|---|---|---|
| `process_status` | `0` | 待处理 |
| `process_status` | `1` | 处理成功 |
| `process_status` | `2` | 处理失败 |

无码业务不使用特殊的自动处理中状态。代理每次处理必须记录：

- `process_result`；
- `process_note`；
- `processed_by`；
- `processed_time`。

## 7. 代理人工处理方案

代理工作台复用现有查询和反馈接口：

```http
GET  /server/markAgent/item/list
POST /server/markAgent/item/{itemId}/feedback
POST /server/markAgent/item/batchMarkSuccess
POST /server/markAgent/item/batchMarkFailed
```

工作台展示：

- 提交用户；
- 号码；
- 无码平台；
- 用户备注；
- 提交时间；
- 处理状态；
- 处理人；
- 处理时间；
- 处理备注；
- 单条成功/失败；
- 批量成功/失败；
- 复制号码和导出。

无码平台工作台隐藏“验证码”列，不触发任何自动检测或第三方请求。

### 7.1 权限和数据范围

代理只能查看和处理自己有权访问的订单。继续使用现有规则：

- `assigned_agent_id`；
- 用户的 `parent_user_id`；
- 用户创建人；
- 用户绑定的平台模板；
- 模板所有者；
- 代理角色和接口权限。

处理接口必须在后端再次检查代理可读范围，不能只依赖前端菜单隐藏。

首期默认三个无码平台由同一所属代理处理，不增加“一个代理只能处理某个无码平台”的平台代理范围表。

## 8. 代理管理与充值方案

现有账号层级保持不变：

```text
管理员
└─ 一级代理
   └─ 下级代理
      └─ 普通用户
```

无码业务不新增独立角色，继续使用现有 `mark_agent`、`mark_sub_agent` 和 `mark_user`。

### 8.1 充值链路

```text
管理员给一级代理充值
  → 一级代理给直属下级代理转次数
  → 下级代理给直属普通用户转次数
  → 普通用户提交时消费次数
```

当前系统不支持跨级充值：

- 管理员不能直接给普通用户充值；
- 一级代理不能跳过下级代理直接给普通用户充值；
- 代理只能给直属下级账号转次数。

### 8.2 充值入口

管理员：

```text
标记业务管理 → 代理管理 → 一级代理 → 充值
```

代理：

```text
标记业务管理 → 代理管理 → 下级代理/普通账户 → 充值次数
```

平台管理中三条无码映射生效后，代理管理的现有平台选项接口会自动返回：

- 无码-泰迪熊；
- 无码-360；
- 无码-腾讯。

首次充值时，系统自动创建对应的 `mark_user_platform_quota` 记录，初始余额为零，不需要提前为每个账号插入余额数据。

### 8.3 充值接口

管理员给一级代理充值：

```http
POST /server/markAgentManagement/admin/recharge
```

代理给直属下级转次数：

```http
POST /server/markAgentManagement/agent/transfer
```

示例：

```json
{
  "requestNo": "唯一充值流水号",
  "targetUserId": 10001,
  "platformCode": "wuma_taidixiong",
  "platformName": "无码-泰迪熊",
  "amount": 1000,
  "reason": "无码平台次数充值"
}
```

### 8.4 余额隔离与计费

三个平台余额分别保存，互不通用：

| 账号 | 平台 | 余额示例 |
|---|---|---:|
| 普通用户A | 无码-泰迪熊 | 1000 |
| 普通用户A | 无码-360 | 500 |
| 普通用户A | 无码-腾讯 | 300 |

消费公式：

```text
订单扣除次数 = 有效号码数量 × 该用户的平台单价
```

首期建议三个无码平台默认单价均为 `1` 次/号码；如果以后不同代理或用户价格不同，继续使用现有模板和用户价格覆盖机制。

代理将号码处理为失败时，系统按该明细的 `item_amount` 自动退回提交用户的平台余额；成功不退款。

充值和转账分别写入：

- `mark_wallet_log`：余额变更流水；
- `mark_agent_point_transaction`：代理充值/转账记录。

`requestNo` 必须唯一，用于防止重复充值。

## 9. 平台模板配置

绑定了平台模板的用户，只能看到模板内声明的平台。因此必须在无码业务对应模板中加入三个新平台：

```json
[
  {
    "platformCode": "wuma_taidixiong",
    "platformName": "无码-泰迪熊",
    "unitPrice": 1
  },
  {
    "platformCode": "wuma_360",
    "platformName": "无码-360",
    "unitPrice": 1
  },
  {
    "platformCode": "wuma_tengxun",
    "platformName": "无码-腾讯",
    "unitPrice": 1
  }
]
```

模板策略建议：

- 新建“无码三平台”模板，避免改动现有普通业务模板；
- 模板归属到实际处理这些订单的代理；
- 只给需要无码业务的用户绑定该模板；
- 如果一个用户还要使用普通业务，需要创建包含普通平台和无码平台的组合模板；
- 禁止通过复用普通平台编码实现组合，否则会破坏完全隔离要求。

## 10. 数据库实施

新增一个可重复执行的迁移脚本，建议文件：

```text
backend/sql/mark_wuma_manual_processing.sql
```

脚本至少包含：

1. 新增三条 `mark_platform_mapping`；
2. 新增用户端“标记无码处理”目录；
3. 新增三个用户端平台菜单；
4. 新增代理端“标记无码处理”目录；
5. 新增三个代理端平台菜单；
6. 给 `admin`、`mark_user`、`mark_agent`、`mark_sub_agent` 绑定相应菜单；
7. 复用现有功能权限菜单；
8. 如需默认模板，插入“无码三平台”模板；
9. 所有插入使用幂等写法，重复执行不会产生重复数据。

菜单 ID 在实施前查询现有最大值和占用情况后确定，不在方案阶段直接写死，避免与当前项目已有菜单冲突。

首期无需修改 `mark_order` 和 `mark_order_item` 表结构，独立平台编码已经能够实现订单、余额、流水和查询隔离。

## 11. 后端实施清单

主要涉及：

- `MarkOrderServiceImpl`
  - 识别 `wuma_*` 为人工直接提交平台；
  - 不执行第三方预查询或自动处理；
  - 保留平台、模板、号码、余额、重复提交和幂等校验；
  - 保留自动分配代理、扣费、失败退款及订单统计。

- `MarkPlatformMappingServiceImpl`
  - 原有映射、菜单过滤、平台开关及排序逻辑原则上直接复用；
  - 验证新增的三级菜单是否需要扩展过滤逻辑。当前过滤逻辑主要识别用户端和代理端的直接子菜单，新增中间“标记无码处理”目录后需要专项验证，必要时改为递归识别平台叶子菜单。

- `MarkAgentManagementServiceImpl`
  - 原有平台选项、管理员充值和代理转账逻辑直接复用；
  - 验证三个新平台能自动出现在充值选项中；
  - 不允许跨平台或跨层级转账。

- `MarkAgentController` / `MarkUserController`
  - 优先复用现有接口；
  - 如前端需要更清晰的业务语义，可增加无码专用路由，但内部仍调用同一订单服务，避免重复实现事务逻辑。

## 12. 前端实施清单

建议新增用户专用页面：

```text
frontend/ruoyi-geek-vue3/src/views/server/mark/user/wuma.vue
```

不建议继续把无码逻辑叠加到已有综合页面的大量平台特判中。专用页面可以复用现有号码提取、确认弹窗、任务记录、备注和导出组件。

代理端复用：

```text
frontend/ruoyi-geek-vue3/src/views/server/mark/agent/process/platform.vue
frontend/ruoyi-geek-vue3/src/views/server/mark/agent/components/ProcessWorkbench.vue
```

代理工作台需要增加无码平台判断：

- 隐藏验证码列；
- 不显示自动检测提示；
- 允许单条成功/失败；
- 允许批量成功/失败；
- 页面标题显示完整的无码平台名称。

代理管理页面原则上无需重写；三条平台映射启用后，现有充值弹窗应自动出现三个无码平台。

## 13. 权限规划

继续复用现有权限：

| 场景 | 权限 |
|---|---|
| 用户查看订单 | `server:markUser:order:list` |
| 用户提交订单 | `server:markUser:order:add` |
| 用户查看详情 | `server:markUser:order:query` |
| 代理查看订单 | `server:markAgent:order:query` |
| 代理处理号码 | `server:markAgent:item:feedback` |
| 代理管理列表 | `server:markAgentManagement:list` |
| 创建代理/用户 | `server:markAgentManagement:add` |
| 平台充值/转账 | `server:markAgentManagement:allocate` |
| 平台管理 | `server:markPlatform:list/add/edit/remove/status` |

平台之间的隔离主要由 `platformCode` 和代理订单查询条件保证，而不是新建三套权限编码。

## 14. 测试计划

### 14.1 平台和菜单

- 三条无码映射启用后，管理员平台管理显示名称和编码；
- 用户只看到其模板允许的无码平台；
- 代理看到三个独立处理入口；
- 关闭任一平台来源后，用户菜单消失且后端拒绝提交；
- 关闭目标或映射后，代理菜单和充值选项同步失效；
- 普通平台菜单和订单不受影响。

### 14.2 充值

- 管理员能够分别给一级代理充值三个平台；
- 一级代理只能给直属下级代理转次数；
- 下级代理只能给直属普通用户转次数；
- 余额不足时转账失败且双方余额不变；
- 相同 `requestNo` 重复提交不会重复入账；
- 三个平台余额互不影响；
- 流水前后余额正确。

### 14.3 用户提交

- 有效号码可以直接提交，不触发预查询；
- 无效号码、空列表和重复号码能正确提示；
- 余额不足时不能创建订单；
- 提交成功后订单、明细、扣费流水一致；
- 相同请求重复提交不产生重复订单；
- 无码订单不进入普通泰迪熊、360、腾讯列表。

### 14.4 代理处理

- 代理只能看到有权限的无码订单；
- 三个平台队列完全隔离；
- 单条成功、失败和批量处理正常；
- 成功不退款；
- 失败只退对应用户、对应平台、对应明细的次数；
- 重复点击处理不会造成重复退款；
- 订单汇总数量和完成状态正确；
- 处理人、处理时间和处理备注完整。

### 14.5 回归测试

- 现有普通泰迪熊、360、腾讯提交与处理正常；
- 原有平台管理开关正常；
- 原有代理创建、充值和转账正常；
- 原有资金流水、模板和菜单过滤正常；
- 管理员、一级代理、下级代理和普通用户的数据范围正常。

## 15. 实施阶段

### 阶段一：数据库和平台配置

- 确定菜单 ID；
- 编写幂等迁移 SQL；
- 增加三个独立平台映射；
- 增加用户端与代理端菜单；
- 配置角色菜单权限；
- 创建无码平台模板。

### 阶段二：用户端直接提交

- 新增无码专用页面；
- 接入号码提取、提交确认和订单记录；
- 接入现有订单创建接口；
- 校验模板、余额、重复提交及平台开关。

### 阶段三：代理人工处理

- 新增三个代理平台入口；
- 调整工作台展示；
- 隐藏验证码和自动检测内容；
- 验证单条与批量成功/失败；
- 验证失败退款。

### 阶段四：代理充值和权限

- 验证三个无码平台自动进入充值选项；
- 测试管理员充值和代理逐级转账；
- 测试角色、菜单和数据权限；
- 核对余额与流水。

### 阶段五：联调、回归和上线

- 执行接口与页面联调；
- 完成业务验收测试；
- 在测试库执行迁移；
- 备份正式库相关表；
- 正式执行迁移并部署；
- 检查菜单、平台、模板、余额和订单流；
- 保留回滚 SQL。

## 16. 验收标准

满足以下条件视为首期完成：

1. 用户菜单存在无码泰迪熊、无码360、无码腾讯三个入口；
2. 三个平台编码与普通业务完全隔离；
3. 用户能够直接批量提交号码且不调用外部接口；
4. 提交时按平台独立扣除次数；
5. 订单自动进入所属代理的对应无码平台队列；
6. 代理能够人工单条或批量处理成功/失败；
7. 失败号码能够准确退款且不重复退款；
8. 用户能够查看任务状态和处理结果；
9. 管理员及代理能够按现有层级为三个平台充值/转账；
10. 平台开关能够同步控制菜单、提交、处理和充值选项；
11. 原有普通标记业务无回归问题。

## 17. 实施前需要最终确认的业务参数

以下参数不影响总体架构，但编码前应确认：

1. 三个平台是否都支持固话，还是仅支持 11 位手机号；
2. 三个平台首期单价是否统一为 1 次/号码；
3. 当日同一号码是否禁止重复提交；
4. 代理标记失败时是否全部自动退款；
5. 代理处理失败是否强制填写失败原因；
6. 一个批次允许提交的最大号码数；
7. 用户是否需要在提交时填写统一备注或逐号备注；
8. 无码三平台由同一代理处理，还是未来需要按平台分配不同代理。

本计划默认采用：支持现有号码规则、单价 1、保留当日防重复、失败自动退款、同一所属代理处理三个平台。
